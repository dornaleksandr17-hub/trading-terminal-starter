# CHANGES_APPLIED_HORIZON_AUDIT_DERIV_RESILIENCE_20260927.md — устойчивость загрузки истории Deriv к сетевым сбоям и выходным

Дата: 2026-09-27.

## Симптом

Реальный прогон `npm run backtest:horizon-audit` на 200-дневном форекс-
диапазоне (2026-03-01..2026-09-17, EURUSD/GBPUSD/USDJPY/AUDUSD) вместо
ожидаемых ~199000 свечей на символ давал сильно заниженные и нестабильные
числа, а на длинных прогонах периодически падал целиком с одной сетевой
ошибкой, теряя часы уже проделанной загрузки. Разбирался по частям в течение
одной сессии, по мере того как каждый следующий симптом вскрывался только
после устранения предыдущего:

1. Первый прогон (после отдельного, более раннего фикса `MAX_DERIV_ITERATIONS`
   200→3000): только 4321 свеча/символ (~3 дня) вместо ~199000, лог
   `[Deriv] stopping: empty batch at iteration 6`.
2. После фикса пункта 1: прогон обрывался целиком с необработанным
   исключением `Deriv WS: connection failed` на случайной итерации (один раз
   — на ~125-й из ~300 ожидаемых), теряя всю историю, накопленную до этого
   момента по всем символам.
3. После фикса пункта 2: прогон стабильно доходил до конца, но
   `candles1mTotal` (165601/символ) был заметно ниже честного расчётного
   максимума (~206040/символ для этого диапазона).

## Причина (по коду)

1. **Пустой батч трактовался как исчерпание источника.** Диагностика через
   `backtest/diag-connectivity.ts` (более ранняя сессия) показала: основной
   Deriv-хост (`ws.derivws.com`, с `app_id`) с сети пользователя недоступен
   на 100% попыток — используется публичный fallback-хост
   (`api.derivws.com`). Этот хост, если ВЕСЬ запрошенный интервал (окно
   ~1000 минут на страницу) целиком приходится на закрытые выходные, отдаёт
   полностью пустой `candles: []`, а не «хвост» последней торговой сессии.
   Старое допущение в коде («forex weekend gaps produce partial batches, not
   empty ones») было неверным именно для этого хоста. `paginateDerivHistory`
   останавливала пагинацию на первом же пустом батче — считая его концом
   истории, хотя это были обычные выходные.
2. **Один сетевой сбой на батче ронял весь прогон.** `fetchDerivBatchWithFallback`
   уже переживает недоступность одного хоста через перебор списка (у каждого
   хоста свой бюджет ретраев — `fetchWithRetry`, 3 попытки с бэкоффом). Но
   если ОБА хоста одновременно исчерпали свои попытки на одном конкретном
   батче (транзиентный сбой сети пользователя посреди многочасового
   прогона — не структурная причина вроде выходных), `fetchDerivBatchWithFallback`
   пробрасывала исключение дальше, а `paginateDerivHistory` вызывала
   `await fetchPage(endTime)` без единого `try/catch` вокруг него — ошибка
   вылетала наружу и обрывала весь прогон целиком, без возможности повторить
   попытку на уже почти скачанном диапазоне.
3. **Пропуск выходных был шире, чем реальный гэп, и терял данные.**
   Константа пропуска пустого батча была выбрана (в рамках фикса пункта 1)
   с запасом в 3 суток (72ч) — чтобы точно перепрыгнуть выходные, не
   зациклившись. Реальный форекс-гэп на выходных — стандартные 48ч (пт 22:00
   → вс 22:00 UTC). На 200-дневном диапазоне это дало измеримую недостачу:
   ожидалось ~206040 торговых минут/символ (200 суток минус 28 полных
   выходных по 48ч), реально получено 165601 — разница 40439 мин ≈ 28 суток,
   при 29 срабатываниях пропуска в логе. Совпадение почти один-в-один с
   гипотезой «лишние 24ч перелёта на каждый прыжок (72ч запас − 48ч реальный
   гэп)»: константа систематически съедала ~14% реальной торговой истории по
   всему диапазону, причём не случайных дней, а конкретно тех, что примыкают
   к выходным — потенциально искажая паттерны с сессионной привязкой
   (`sessionAgnostic`, session-based анализ).

## Что изменено

`backtest/data-loader.ts`, функция `paginateDerivHistory`:

- Добавлен счётчик `consecutiveEmptyBatches` и константы
  `EMPTY_BATCH_SKIP_SECONDS` / `MAX_CONSECUTIVE_EMPTY_BATCHES`. Пустой батч
  больше не останавливает пагинацию немедленно: код прыгает на
  `EMPTY_BATCH_SKIP_SECONDS` назад и повторяет запрос на том же диапазоне
  дальше в прошлое; сдаётся (легитимная остановка) только после
  `MAX_CONSECUTIVE_EMPTY_BATCHES` пустых батчей подряд — это уже не похоже на
  обычные выходные.
- Отдельно, симметрично, но не путая одно с другим: добавлен счётчик
  `consecutiveFetchErrors` и константы `FETCH_ERROR_RETRY_BASE_DELAY_MS` /
  `MAX_CONSECUTIVE_FETCH_ERRORS`. Вызов `fetchPage(endTime)` обёрнут в
  `try/catch`; при сетевой ошибке — до 5 повторов подряд с нарастающим
  бэкоффом (2с/4с/8с/16с) на ТОМ ЖЕ `endTime` (не пропуская диапазон, в
  отличие от пустых батчей — здесь речь не о «данных нет», а о «не удалось
  спросить, есть ли данные»); сдаётся, пробрасывая исключение дальше (прогон
  всё равно легитимно падает), только после 5 подряд — это уже похоже на
  настоящий продолжительный обрыв связи, а не на секундный блип.
- `EMPTY_BATCH_SKIP_SECONDS` сужен с 3 суток (72ч) до 54 часов (48ч реальный
  форекс-гэп + 6ч запас на расхождения в расписании/DST) — в 4 раза меньше
  лишнего перелёта, чем раньше. `MAX_CONSECUTIVE_EMPTY_BATCHES` (3) оставлен
  без изменений: 3×54ч ≈ 6.75 суток по-прежнему с запасом покрывает и
  праздничные закрытия (Рождество/Новый год).
- `MAX_DERIV_ITERATIONS` (200→3000) и многохостовый fallback
  (`getDerivWsUrls`/`fetchDerivBatchWithFallback`) — из более ранних, уже
  применённых фиксов этого же диагностического цикла; в этот файл изменений
  не вносились, упомянуты здесь для полноты картины, так как все три фикса
  взаимодействуют в одном и том же цикле пагинации.

`.gitignore`: добавлен `backtest/output-run/` — рабочий (не версионируемый)
каталог для результатов диагностических прогонов, использованных при разборе
этих багов; ранее случайно попал в коммит вместе с ещё не финальным прогоном.

## Тесты

`backtest/data-loader.test.ts` — было 6 тестов, стало 8:

- Обновлены существующие: `skips over a single empty batch...` теперь
  проверяет прыжок на 54ч (было 3 суток) — падает на старом коде (72ч),
  проходит на новом; комментарий у `gives up after 3 consecutive empty
  batches...` уточнён (6.75 суток вместо 9).
- Новые: `retries the same batch after transient fetch errors and keeps
  collecting (not truncated)` и `gives up after 5 consecutive fetch errors
  and rethrows (real outage, not a blip)` — используют `vi.useFakeTimers()` +
  `vi.runAllTimersAsync()`, чтобы не ждать реальный бэкофф (до 30с) в
  юнит-тесте.

Полный набор на момент фиксации: 88 файлов, 1155 тестов, все зелёные;
`npm run typecheck` и `npm run lint` чистые.

## Реальный прогон (подтверждение на практике)

После применения всех пяти фиксов и очистки обоих кэшей
(`backtest/.candle-cache`, `backtest/.cache`) реальный прогон
`backtest:horizon-audit` на том же 200-дневном диапазоне:

- Первая попытка (только фиксы 1–4, ещё с 72ч): 165601 свеча/символ — баг 5
  ещё не был найден на этом этапе.
- После фикса 5 (54ч): EURUSD — 195841 свеча (было 165601), заметно ближе к
  честному расчётному максимуму ~206040. Прогон в этот раз не был доведён до
  конца во всех символах — оборвался на GBPUSD, но легитимно, после честных
  5 попыток с бэкоффом (`giving up after 5 consecutive fetch errors ...
  this looks like a real outage, not a blip`) при реальном продолжительном
  (30+ секунд) обрыве связи, а не из-за ошибки в логике.
